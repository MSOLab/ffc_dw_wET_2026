## 질문

선행 세 문서는 NEH-CP를 **한 번** 돌리고 flow를 거기서 끊었다. 이 런은 같은
유도 순서 기능을 고정된 **전체 flow** 위에서 묻는다:

`dispatch_v4 -> MCF-LB -> FMM -> NEH-CP(s) -> ISW-CP -> base CP`

1. NEH-CP를 여러 번 돌리며 매번 직전 패스가 만든 스케줄에서 순서를 다시 유도하는
   것이 **end-to-end로** 값어치가 있는가?
2. 몇 패스가 좋은가? 한계 수익은 어디서 끊기는가?
3. 1440 그리드의 모드 순위(`completion` < `midpoint` < `first_stage`)가 이
   슬라이스에서도 재현되는가?

## 남은 교란 / 한계

1. **등배분 비교가 아니다** (결과 0). 3패스는 NEH에 3배 예산을 쓰므로 "순서 재유도"와
   "NEH 시간 증가"가 교란돼 있다. 가르려면 `completion` 단독에
   `total_timelimit: 0.0324nc`를 준 대조군이 필요하고, 이 런에 없다.
2. **160 인스턴스, 단일 (T,R) 셀이다.** 이 저장소에는 이미 파일럿(3 인스턴스, 같은
   `(0.6, 0.2)` 셀)의 prefix 결론이 1440 그리드에서 **방향까지 뒤집힌** 전례가 있다
   (`neh_cp_seq_source_full.md` "파일럿과의 불일치는 population effect다"). 여기서
   얻은 패스-수 결론을 그리드 전체로 일반화하지 말 것.
3. **run-to-run 노이즈**. replicate 문서가 잰 flow 기준 1440-인스턴스 평균의
   run-to-run SE ≈ 0.29 pp를 160 인스턴스로 환산하면 ≈ 0.87 pp다. 이 문서의 통계는
   **같은 run 안**에서 인스턴스별로 paired 대비한 값이므로 그 SE가 아니라 paired CI가
   맞는 잣대이지만, 3패스의 최량 단일 대비 이득이 **0.60 pp**로 그 환산값보다
   작다는 점은 기억할 것. 독립 replicate 없이 2 σ대 결론을 강하게 주장하지 않는다.
4. **`solve_base_model_cpsat`는 죽은 스텝이다.** 1120런 전부에서 도달하지 않았으므로
   이 config의 flow는 실질적으로 6스텝이다.

## 조치 제안

1. **기본값을 3패스로 바꾸지 않는다 — 아직은.** flow 기준 최량이긴 하나 최량 단일
   대비 0.60 pp / 2.2 σ이고 위 한계 3이 걸린다. 바꾸기 전에 두 가지를 먼저 잰다:
   (a) `completion` 단독에 `0.0324nc`를 준 **등배분 대조군**,
   (b) 같은 config의 **독립 replicate**.
2. **`0.0108nc` × 2패스(`completion -> midpoint`)는 지금도 무해한 기본값 후보다.**
   9개 체인 대비가 전부 음수이고 NEH 기준으로는 4.2–4.7 σ로 유의하며, 3패스보다 꼬리를
   덜 깎는다 (ISW 등록 2.79 vs 2.19).
3. **4패스는 시험하지 않는다** (결과 3의 체감).
4. **config에서 `solve_base_model_cpsat`를 빼거나** ISW-CP 예산을 명시적으로 잘라
