Dispatching / Job-Priority Rule Reference

Branch: 20260624_more_init_dispatch · Code: src/ffc_ddw_sum_et/parameters/ffc_ddw_params.py, src/ffc_ddw_sum_et/parameters/sorter.py · 2026-06-25

At a glance

  • 17 dispatch keys across 5 groups, all targeting weighted E+T minimization
  • Each key is decoded in two directions: sd_ (forward FAM) and rd_ (reverse pipeline)
  • wxd2 is the current paired-best single rule (analysis v2, m=1)
  • All keys sort ascending; last component is always pos (deterministic tie-break)

Objective function

Weighted early + tardiness — all rules aim to minimize this:

Σj [ w−j·max(d−j−Cj, 0) + w+j·max(Cj−d+j, 0) ]

All rules produce an initial dispatch order (tie-break before Cj is known). Every key sorts ascending, with pos as the final deterministic component.

Decode direction: sd_ vs rd_

Two decode pipelines per priority sequence

priority order→ sd_ simple→ FAM forward decode→ IIT correction→ weighted E+T
priority order→ rd_ reverse→ same IIT→ reverse candidate select (best by makespan)→ weighted E+T

Same priority, different sd/rd results. Pan et al. (2017) decode shares the sd_ skeleton.

Code & registration map

How a sweep key resolves to a forward priority sequence. The getters live in ffc_ddw_params.py; sorter.py owns the two key vocabularies (DispatchSeqKey, ParamSortKey) and the two dispatchers that map a key to its getter.

  • ffc_ddw_params.py — defines the 17 get_*_job_sequence() getters (+ helpers _center_penalty_job_sequence, get_job_2_due_date_star_map).
  • sorter.py — owns DispatchSeqKey (17 sweep keys) → dispatch_seq_job_sequence, and ParamSortKey (6 alias keys) → param_sort_job_sequence; the 4 shared keys (weight_due_pos, due_weight_pos, due2_weight_pos, due_star_weight_pos) delegate across.
  • callers — sweep configs / controller drive both sd_ and rd_ decode; the IO heatmap imports only the lightweight ParamSortKey surface (no full params chain).

4. wxd family — 2-way partition + within-group sort

Common step 1: partition all jobs into early/late using additive aversion scores relative to d̄.

earliness_aversion[j] = w−j + (d−j − d̄)     # higher = dislikes early completion
tardiness_aversion[j] = w+j + (d̄  − d+j)     # higher = dislikes late completion

Jobs with higher tardiness_aversion go to the early group (front); lower goes to the late group (back). Result = sorted(early) ++ sorted(late).

KeyTie handlingEarly-group sort (asc)Late-group sort (asc)
wxd1midpoint split (dmid<d̄)(w+−2w−+2w_max)(dmid−d̄)(w−−2w++2w_max)(dmid−d̄)
wxd2tie → late(w+−2w−+2·ew_max)(d−−d̄)(w−−2w++2·tw_max)(d+−d̄)
wxd3tie → early−tpj(d̄) = −w+·max(d̄−d+,0)epj(d̄) = w−·max(d−−d̄,0)
wxd4tie → early−tpj(baseline)epj(baseline)

ew_max = max w−, tw_max = max w+, w_max = max(ew_max, tw_max).
wxd1 partitions by midpoint sign; wxd2 partitions by aversion-score comparison.
wxd4 baseline = max( minj rj + Σearly p_last_j / m_last, d̄ ) (estimated completion when early group finishes last stage; partition still uses d̄).

wxd2 magic constant 2 (core)

Sort key = Ce · (d−−d̄), where Ce = w+ − 2w− + 2·ew_max = w+ + 2(ew_max − w−) ≥ 0.

1. +2·ew_max = forced minimum sign stabilizer

core
For the product sign to cleanly equal sign(d−−d̄), we need Ce ≥ 0. In the worst case (w−=ew_max, w+=0): (k−2)ew_max ≥ 0 ⇔ k ≥ 2. If k=1, the coefficient flips negative and sorting reverses.

2. −2w− = earliness:tardiness = 2:1 exchange rate

policy
Early group is already selected as "net tardiness-averse" in partition, so within-group order should be dominated by residual risk: earliness. 2 is the minimum integer that makes earliness strictly dominant. Result: low-earliness jobs go to the front, high-earliness jobs to the back (near center = latest completion in block).

3. Multiplicative (d−−d̄) (ungated) beats wxd3/4 gated penalty

robustness
wxd3/4's max(·,0) penalty collapses to 0 when a window straddles d̄ in a dense block, losing ordering information. wxd2's affine surrogate maintains a continuous rank.

Why wxd2 over wxd3/wxd4

✓ wxd2 — picked (paired-best, m=1)

Within-group key is the ungated affine surrogate Ce·(d−−d̄).

Every job gets a distinct continuous rank, even when its realized penalty at d̄ is exactly 0 — the dispatch order is decided before completion times are known.

tie-break before Cj is known → no collapse

✗ wxd3 / wxd4 — did not beat wxd2

Swap the surrogate for the actual gated penalty w·max(·,0) at a reference time.

In the dense straddling block (d+≥d̄) the penalty is 0 for many jobs → they tie and fall back to native pos, discarding order exactly where the block is densest.

wxd4 only moves the reference to an estimated completion baseline — same gating

Detailed justification: this branch conversation / analysis/20260624_dispatch_init_justification_2.md.
Current paired-best single rule = wxd2 (analysis v2, m=1).

5. cpd family — center-penalty single lexicographic (parameterless)

All jobs sorted by a single key (_center_penalty_job_sequence(center)):

ep_j = w−j · max(d−j − center, 0)      # early penalty
tp_j = w+j · max(center − d+j, 0)      # tardy penalty
key  = (−tp_j, ep_j, d+j, pos)          # ascending
  • Tardiness leads the key (−tp desc): tardiness is irreversible, but earliness is recoverable via insert_idle_time → heavy-tardiness jobs go first.
  • Earliness as tie-break, then EDD+ (d+) for the central block (tp=ep=0, windows straddling center). This generalizes wxd's hard partition into a single-key smooth sort.
