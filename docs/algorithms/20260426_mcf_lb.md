# MCF-LB Phase 2 Cumulative Heuristic & Value Resolver

`run_mcf_lb_4`의 Phase 2에서 CP-SAT 대신 누적 재삽입 휴리스틱을 사용할 수 있게 하고,
시간 제한 표현식을 `nc` / `c` / `m` 세 가지 후위 연산자로 확장한다.

---

## 1. 누적 재삽입 휴리스틱 (`cumulative_heuristic.py`)

`solve_last_stage_with_profile_fix` 의 drop-in 대안으로, CP-SAT 솔버 없이
last-stage-only 스케줄을 개선한다.

### 알고리즘

1. **초기 시퀀스 구성** — `reference_schedule` 의 마지막 스테이지 작업들을
   `(start_time, end_time, instance_job_index)` 기준으로 정렬하여 시퀀스로 만든다.
2. **시작 평가** — 시퀀스를 `dispatch_stage_by_jobs(..., force_job_id_seq_as_priority=True)`
   로 배분하고 `insert_idle_time` 을 적용한 후 가중 E+T 목적함수를 계산한다.
3. **반복 개선** — `_timed_out()` 이 될 때까지 다음 루프를 돈다:
   - 각 잡 $j$ 의 현재 기여도 $\_contribution(j)$ 를 계산하고 내림차순 정렬:
     $$\_contribution(j) = w_e^j \cdot \max(d_j^- - c_j, 0) + w_t^j \cdot \max(c_j - d_j^+, 0)$$
   - 정렬된 순서대로 잡을 하나씩 제거하고 삽입 위치를 스캔:
     - **Earliness** ($c_j < d_j^-$) → 뒤쪽으로 밀기 → `range(current_pos + 1, range_end)`
     - **Tardiness** ($c_j > d_j^+$) → 앞쪽으로 당기기 → `range(range_start, current_pos)`
     - **On-time** ($d_j^- \leq c_j \leq d_j^+$) → 스킵
     - `insert_radius` 가 설정되면 스캔 범위를 제한
   - 각 후보 위치에서 `_evaluate(trial)` 로 목적함수를 재계산하고 가장 낮은 값을 선택
   - 개선된 위치가 있으면 시퀀스를 업데이트, `progress` 에 기록
   - `first_improvement_restart=True` 이면 첫 개선 시 즉시 다음 패스로 이동
4. **종료** — 한 패스에서 개선이 없거나 시간 초과 시 종료

### 반환값

| 필드 | 내용 |
| --- | --- |
| `result` | `LastStageSolveResult(schedule, objective, bound, j_i_2_end, makespan)` |
| `solve_sec` | 총 경과 시간 |
| `status_name` | `"HEURISTIC"` |
| `progress` | `[(elapsed, obj), ...]` — 초기값 + 각 개선 시점 |
| `scan_stats` | `{"mean_sec", "max_sec", "n_scans", "n_passes", "n_considered", "n_moves"}` |

### Phase 2 통합

`use_heuristic=True` 일 때:

- Phase 1 시드 중 `init_schedule` 의 가중 E+T가 가장 낮은 단일 시드만 선택
- 나머지 시드와 CP-SAT 관련 파라미터는 무시
- `diagnostic.heuristic_progress_per_seed` 와 `heuristic_scan_stats_per_seed` 에
  진행 상황 기록 (CP-SAT 경로에서는 비어 있음)

## 2. 값 표현식 해석기 (`value_resolver.py`)

기존 `tl_resolver.resolve_cp_tl` 을 대체하는 범용 해석기로, YAML 설정에서
사용하는 문자열 표현식을 숫자로 변환한다.

### 표현식 규칙

| 형식 | 계산 | 예시 |
| --- | --- | --- |
| `float` | 그대로 | `300.0` → 300.0 |
| `"<n>nc"` | $n \times \text{job\_count} \times \text{stage\_count}$ | `"0.01nc"` |
| `"<n>c"` | $n \times \text{stage\_count}$ | `"2c"` |
| `"<n>m"` | $n \times \text{last\_stage\_mc\_count}$ | `"3m"` |
| `None` | `None` (제한 없음) | `null` |

`"nc"` 는 잡 수와 스테이지 수 모두에 비례하는 시간 제한, `"c"` 는 스테이지 수만,
`"m"` 은 마지막 스테이지의 병렬 기계 수에만 비례한다.

### 추가된 `last_stage_mc_count` 속성

`FFcParameters` 클래스에 `last_stage_mc_count` 캐시된 속성을 추가하여
마지막 스테이지의 병렬 기계 수를 `resolve_value_expr` 에서 `"m"` 표현식에 사용한다.

**관련 파일**

| 역할 | 파일 |
| --- | --- |
| 해석기 | [value_resolver.py](../../src/ffc_ddw_sum_et/orchestration/value_resolver.py) |
| 파라미터 속성 | [ffc_params.py](../../src/ffc_ddw_sum_et/parameters/ffc_params.py) |

## 5. 실험 결과

인스턴스 2개(`n=50` / `n=200`), `last_stage_only_tl: "0.01nc"` 고정,
`insert_radius` 를 변화시키며 진행. 모든 run에서 `use_heuristic: true`.
노트북(125H)에서 계산 수행.

> scan_stats(`n_passes` / `n_considered` / `n_moves`) 는 `20260427T014536` 부터 기록.
> `20260426T222003` 은 `last_stage_only_cp_tl` 키(이후 rename)를 사용하고, scan_stats 미기록.

- `radius=20`: scan당 비용(0.202 s) 증가로 TL 내 99 scans 밖에 못 함 → 커버리지 감소 → 역전.
